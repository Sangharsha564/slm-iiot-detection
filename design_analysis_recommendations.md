## 1. Where Does the Domain Knowledge Come From?

Domain knowledge in this architecture serves a precise purpose: it tells the decoder SLM what it cannot know from the numeric features alone — the *mechanism* of each attack, what the features mean in a network context, and what normal traffic looks like. The knowledge must be accurate, specific to your attack types, and sourced from authoritative references. Here is exactly where each type comes from.

### 1.1 Attack Mechanism Descriptions (for Slowloris, RUDY, Slowread)

These are manually curated from the academic literature and vulnerability disclosures. Specific sources:

- **Slowloris:** Originally documented by RSnake (Robert Hansen) in 2009. Mechanism papers: F1-3 (slowTrack), F1-10/F1-11 (survey taxonomy papers in your Folder 1). The attack exploits HTTP/1.1's requirement that a server must wait for a complete request header before responding (RFC 7230, Section 3.5). The domain knowledge text should describe: "Slowloris sends GET headers one line at a time, every 8–15 seconds, preventing header completion while keeping the connection alive."

- **RUDY (R-U-Dead-Yet / Slowbody):** Documented in vulnerability databases (CVE-2012-xxxx pattern). Mechanism from F1-11 survey and F3-5 (ShieldGPT). Exploits HTTP's Content-Length field: POST a declared body of 1,000,000 bytes but transmit 1 byte per 10 seconds. Server must hold the socket open for the entire Content-Length regardless.

- **Slowread:** Described in F1-10 survey. Exploits TCP's flow control: the client advertises a near-zero TCP receive window size (TCP Window = 0–64 bytes), forcing the server to hold the connection open while waiting for the client's window to increase. The client never opens its window.

**Where to write these:** You hand-write these as 3–5 sentence descriptions in the SSRP system prompt template file. They are based on the mechanisms you have already studied through your paper reading. This is static text — not generated by any model.

### 1.2 Normal Traffic Baselines (What "Normal" Looks Like)

These are computed from your CIC IIoT 2025 training data. After preprocessing, you calculate per-feature statistics across all benign-labeled flows:

```python
benign_flows = df[df["label"] == "Benign"]
baseline = {
    "flow_duration": {"mean": benign_flows["flow_duration"].mean(),
                      "std": benign_flows["flow_duration"].std(),
                      "p95": benign_flows["flow_duration"].quantile(0.95)},
    "pkt_rate":      {"mean": benign_flows["pkt_rate"].mean(), ...},
    ...
}
```

These statistics become the "normal behavior norms" injected into the SSRP system prompt: "Legitimate HTTP connections on this IoT network complete within 0.1–4.2 seconds (mean 1.8s). Normal pkt_rate is 22–180 pkt/s." These are dataset-specific and must be computed from your CIC IIoT 2025 benign traffic — not taken from prior papers, because IoT traffic distributions differ from cloud or enterprise traffic.

### 1.3 Protocol Definitions (TCP, HTTP, Zeek States)

These come from authoritative protocol specifications:

- **TCP state machine:** RFC 793 (Transmission Control Protocol). Zeek's `conn_state` codes are documented in Zeek's official documentation (https://docs.zeek.org/en/master/scripts/base/init-bare.zeek.html).
- **HTTP header structure:** RFC 7230 (HTTP/1.1 Message Syntax and Routing). The definition of a "complete" HTTP header (ending in `\r\n\r\n`) is from this RFC.
- **TCP window size:** RFC 793, Section 3.1. The window field is a 16-bit value (0–65,535 bytes, or larger with window scaling per RFC 7323).

In practice, you write short, plain-language summaries of these definitions. Example: "TCP conn_state S1 = SYN and SYN-ACK exchanged, connection established, but no application data has been transferred by either party." You do not paste RFC text — you write the simplified version relevant to your attack signatures.

### 1.4 Feature Definitions (What Each of the 12–15 Features Means)

Written manually by you, based on your feature engineering work. Each definition is one sentence:
- "flow_duration: the total seconds from the first SYN packet to the last observed packet or connection close event."
- "header_completeness: the fraction of HTTP request headers received relative to a complete request (1.0 = full header received, including final CRLF)."
- "pkt_rate: total packets divided by flow_duration, measured in packets per second."

These definitions are specific to your Zeek-extracted feature set and your verbalization format.

### 1.5 Summary: Domain Knowledge Sources

| Knowledge type | Source | Static or computed |
|---|---|---|
| Attack mechanism descriptions | Academic papers (F1-3, F1-10, F1-11), CVE databases | Static — manually written |
| Normal traffic baselines | CIC IIoT 2025 training data statistics | Computed from your dataset |
| TCP/HTTP protocol definitions | RFC 793, RFC 7230, Zeek documentation | Static — manually written |
| Feature definitions | Your feature engineering choices + Zeek docs | Static — manually written |
| Exemplar explanations (3–5 per attack type) | Teacher LLM (GPT-4/Claude) + human review | Semi-automated — generated offline |

All domain knowledge is assembled once before deployment. It does not change at runtime. None of it comes from the trained models themselves — it is injected into those models as context.

## 2. Specific Contribution and Responsibility of Each SLM

These two models are architecturally different types of neural networks. Their responsibilities do not overlap.

### 2.1 Encoder SLM — Responsibility

**Type:** Discriminative BERT-class transformer (reads whole input simultaneously, bidirectional attention).

**Primary responsibility: Classification and representation.**

The Encoder SLM receives the verbalized flow features and must answer one question: "Which class does this flow window belong to?" It does this by:

1. Reading the entire input token sequence simultaneously
2. Building contextual representations of each token via multi-head self-attention
3. Condensing the full input into the `[CLS]` embedding — a fixed-size vector capturing the overall "meaning" of the flow pattern
4. Mapping the `[CLS]` embedding to a probability distribution over attack classes via the classification head

**What the Encoder SLM contributes:**
- The authoritative detection label (Slowloris / RUDY / Slowread / Benign)
- The confidence score (0–1) for that label
- The `[CLS]` embedding — a dense, learned, contextual representation of the attack pattern, usable for exemplar retrieval
- Cross-feature interaction understanding through attention — it learns that `flow_duration = 127.5s` combined with `header_completeness = 0.12` is Slowloris, while the same `flow_duration` combined with `content_length_ratio = 0.001` is RUDY

**What the Encoder SLM does NOT do:**
- It does not generate any natural language
- It does not explain its own decision
- It does not produce SHAP values
- It does not reason about why the classification is correct

**Why it must be the Encoder (not the Decoder) for detection:**
The encoder processes all input tokens simultaneously (bidirectional). This means it "sees" the entire feature context before making a decision — `pkt_rate` and `header_completeness` inform each other through attention. A decoder, by contrast, reads left to right and generates one token at a time. This is ideal for text generation but suboptimal for classification, where the full context of all features should influence the decision simultaneously.

### 2.2 Decoder SLM — Responsibility

**Type:** Generative GPT-class transformer (autoregressive, reads input then generates output one token at a time, left to right).

**Primary responsibility: Explanation generation.**

The Decoder SLM receives a text prompt (containing the SIR, an exemplar, and domain knowledge) and generates a structured natural language explanation of why the detected traffic is classified as the predicted attack type.

**What the Decoder SLM contributes:**
- The `observation` — a neutral factual description of what was observed
- The `evidence` — specific, feature-grounded reasoning linking observed values to attack signatures
- The `conclusion` — a coherent explanation of the attack mechanism
- The `mitigation` — actionable response recommendations tailored to the specific attack subtype

**What the Decoder SLM does NOT do:**
- It does not independently classify the traffic
- It does not run SHAP or compute feature attribution
- It does not access the raw network traffic
- It does not override the Encoder SLM's classification (it takes the label as given)

**Why it must be the Decoder (not the Encoder) for explanation:**
Text generation requires an autoregressive architecture. BERT-class encoders cannot generate sequential text — their architecture produces a fixed-size output vector, not a variable-length sequence. Generating a 300-token explanation requires a generative model that produces token-by-token output conditioned on all previous tokens and the input prompt. This is precisely what GPT-class decoders do.

### 2.3 The Division of Labour — Why It Is Optimal

```
Encoder SLM          Decoder SLM
─────────────────    ─────────────────────────────────────
"What is it?"        "Why is it that? What does it mean?
                      What should we do?"

Discriminative       Generative
Bidirectional        Autoregressive
11–22M parameters    2.7–4B parameters
~80ms inference      ~1–3s inference
Runs synchronously   Runs asynchronously
Classification task  Language generation task
BERT-class           GPT-class
```

Neither can do the other's job. This is not an arbitrary design choice — it is a consequence of the fundamental architectural differences between discriminative and generative transformers.

## 3. Is SHAP + SIR + Decoder the Best Approach?

This is the most important design question in the system. Let us examine every realistic alternative against the proposed approach.

### 3.1 Option A — Decoder-Only, No SHAP, No SIR

Pass the raw verbalized features and the detection label directly to the decoder:

```
Input to decoder: "The following flow was classified as Slowloris with 97% confidence.
Flow features: FLOW_DURATION: 127.5s PKT_RATE: 0.03 HEADER_COMPLETE: 0.12 ...
Explain why."
```

**What happens in practice:**

With a 4B model and no exemplars: catastrophic failure. Paper F3-6 (Rethinking On-Device) demonstrates Gemma3-4B with no few-shot exemplars achieves F1=0.05 on explanation-grounded classification tasks on numeric IoT data. The model either generates generic security advice unrelated to the specific feature values, or confidently explains the wrong attack mechanism.

With a 4B model and exemplars but no SHAP: moderate performance. The model can pattern-match from the exemplar, but without being told which features are the discriminative ones, it may latch onto salient but irrelevant values (e.g., commenting on `dst_port: 80` being HTTP rather than on `header_completeness: 0.12` being the Slowloris signature). Paper F3-4 (eX-NIDS) measures this: explanation correctness without feature attribution = ~36%.

**Verdict:** Viable but substantially worse. Correctness drops from ~80% to ~36%.

### 3.2 Option B — All Features in SIR, No SHAP Ranking

Include all 12–15 features in the SIR with their values and directions, but do not compute SHAP — do not rank them or compute importance scores:

```json
{
  "detection_label": "Slowloris",
  "all_features": [
    {"name": "flow_duration", "value": "127.5s", "direction": "high"},
    {"name": "pkt_rate", "value": "0.03", "direction": "low"},
    ... (all 12–15 features)
  ]
}
```

**What happens in practice:**

The decoder receives all features equally. For a good model with strong exemplars, this works reasonably well — the model can learn from the exemplar which features tend to matter for Slowloris and apply that knowledge. Feature Consistency (does the explanation cite real features?) is maintained because all features are provided. However:

- Explanation correctness may be lower than SHAP-guided (~60–70% vs ~80%) because the model may emphasize the wrong features in edge cases
- The SIR is longer (all 12–15 features vs top 4–6), consuming more context window tokens
- No importance weighting means the decoder treats `dst_port: 80` (negligible importance) equally with `header_completeness: 0.12` (primary Slowloris signature)

**Verdict:** A valid simplification with moderate quality trade-off. Suitable if Tree SHAP is unavailable or if you want to minimize system complexity. The output is still grounded (no hallucination of feature values) but the emphasis may be suboptimal.

### 3.3 Option C — SHAP + Templates, No Decoder SLM

Compute SHAP values, format top features into a fixed template:

```
ALERT: Slowloris (confidence: 0.97)
Key indicators:
  • flow_duration = 127.5s (55× above normal 2.3s) — HIGH
  • pkt_rate = 0.03 pkt/s (1572× below normal) — LOW
  • header_completeness = 0.12 (88% missing) — LOW
Attack type: Slowloris (incomplete HTTP header connection exhaustion)
Recommended action: Enforce 10s server-side header timeout.
```

**What happens in practice:**

This is fast (no decoder needed), deterministic (same input always produces same output), and guaranteed to cite correct features. But it is rigid. The template cannot:
- Explain WHY `header_completeness = 0.12` indicates Slowloris specifically and not RUDY
- Connect the feature values to the attack mechanism in natural language
- Handle edge cases where the attack pattern is atypical (e.g., Slowloris with slightly higher pkt_rate due to randomization)
- Generate context-sensitive mitigation advice (e.g., "given that this IoT device serves HTTP only on port 80...")

For a security analyst, a template output reads like a formatted data dump. It conveys the same information as looking at the SHAP plot directly, just slightly reworded. A decoder explanation reads like a junior analyst wrote it — it makes the connection between evidence and mechanism explicit.

**Verdict:** Good enough for a baseline comparison in your thesis, but insufficient for the research contribution you are claiming (XAI-grounded SLM explanation generation).

### 3.4 Option D — The Proposed Approach: SHAP + SIR + Decoder

The full pipeline as designed: SHAP ranks the most important features, SIR packages them with semantic context (direction, baseline comparison, interpretation), decoder generates a grounded explanation.

**What the evidence shows:**
- eX-NIDS (F3-4): augmented prompt with feature attribution raises correctness 36% → 80%+
- SSRP framework (F3-9): 16-factor structured prompt raises explanation quality ~40% in 2–4B models
- F3-6: few-shot exemplars raise performance from F1=0.05 to F1=0.85 for Gemma3-4B

**The combination that makes this work:**
1. SHAP tells the decoder WHICH features to focus on (reducing the search space from 12–15 to 4–6)
2. SIR tells the decoder WHAT each feature value means relative to normal (so it can say "abnormally high" with a specific baseline)
3. Exemplar shows the decoder HOW to structure the reasoning for this attack type
4. Domain knowledge tells the decoder WHY those features indicate that specific mechanism

Each element addresses a specific failure mode. Removing any one of them degrades quality in a measurable way.

**Verdict:** Best approach for explanation quality. Justified by strong empirical evidence from multiple papers. The additional complexity (SHAP computation, SIR construction) adds less than 200ms total and is computationally negligible compared to the decoder's 1–3s inference time.

## 4. Could We Rely Mainly on Decoder SLM and Avoid SHAP/LIME/SIR?

Yes, technically. But with significant quality cost. Here is the honest assessment:

**If you skip SHAP and SIR entirely, the minimum viable decoder pipeline is:**

```
Verbalized features string + detection label + few-shot exemplar → decoder prompt
```

Without SHAP: the decoder must infer which features matter from the exemplar alone. For a small exemplar library (15–25 examples), the model generalizes reasonably if the incoming alert closely matches an exemplar. If the alert is atypical (randomized Slowloris with variable keepalive timing, for example), the decoder has no attribution guidance and may focus on the wrong features.

Without SIR structure: feature values appear in the prompt as text, but without importance rankings, baseline comparisons, or semantic interpretations. The decoder cannot say "55 times above normal" because it does not know what normal is unless you provide it separately (which is essentially a simplified SIR).

**Simplified alternative that preserves most quality:**

Keep the SIR but compute feature selection by a simple rule rather than SHAP:
1. Use the top-N features by MI ranking (already computed during feature selection training)
2. Include all N features in the SIR with their values and pre-computed baselines
3. Skip SHAP at inference time entirely

This eliminates the SHAP computation (<100ms, admittedly negligible) and the XGBoost dependency at inference time. Quality would be slightly lower than SHAP-guided (because MI ranks features globally, not for each specific prediction), but meaningfully higher than decoder-only with no structure.

**Recommendation on skipping SHAP:** Do not skip it. Tree SHAP on XGBoost takes less than 100ms, which is negligible. It adds no significant latency. It measurably improves explanation quality. The only reason to skip it would be to reduce system complexity, and the complexity it adds (three lines of Python code) is trivially small. Keep SHAP.

## 5. XAI Methods vs Decoder-SLM Reasoning: Full Trade-off Analysis

### 5.1 Traditional XAI Methods (SHAP, LIME)

| Property | Detail |
|---|---|
| Speed | Tree SHAP: <100ms. Kernel SHAP (neural): 5–30s. LIME: 1–5s. |
| Accuracy of attribution | Tree SHAP: mathematically exact. Kernel SHAP/LIME: approximate, sample-dependent |
| Output format | Numerical scores per feature. Requires human interpretation. |
| Consistency | Deterministic — same input always produces same output |
| Hallucination risk | Zero — output is mathematical, not generated |
| Explanation depth | Shallow — tells you which features matter, not why they matter mechanistically |
| Adaptability | None — same format regardless of attack type or context |
| Suitable for non-experts | No — requires knowledge of what SHAP values mean |
| Computable without LLM | Yes |
| Memory footprint | Negligible |

### 5.2 Decoder SLM Reasoning (Generative Explanation)

| Property | Detail |
|---|---|
| Speed | 1–3s (server), 30–150s (Raspberry Pi-class hardware) |
| Attribution accuracy | Dependent on prompt quality and fine-tuning. Can hallucinate without SHAP grounding |
| Output format | Natural language — readable by any security analyst |
| Consistency | Non-deterministic (temperature > 0) — varies slightly between runs |
| Hallucination risk | Moderate without SHAP/SIR. Low with SHAP/SIR. |
| Explanation depth | Deep — can explain mechanism, provide context, discuss attacker intent |
| Adaptability | High — adapts explanation to specific feature combination and context |
| Suitable for non-experts | Yes — the primary advantage |
| Computable without ML model | No — requires 2–4B parameter model |
| Memory footprint | 1.7–2.5GB (Q4_K_M) |

### 5.3 The Hybrid (Current Architecture)

The SHAP + SIR + Decoder combination is not simply "better than both" — it is qualitatively different. SHAP provides mathematically grounded attribution that prevents the decoder from inventing reasons. The decoder provides human-readable depth that SHAP alone cannot achieve. The SIR is the bridge that translates SHAP's numerical output into the semantic context the decoder needs.

This combination has one important property neither SHAP alone nor the decoder alone can achieve: **verifiably grounded natural language explanation**. The explanation is both readable (decoder advantage) and anchored to the actual features that drove the decision (SHAP advantage). You can verify it is grounded using the eX-NIDS Feature Consistency metric — every feature cited in the explanation must exist in the SIR.

### 5.4 The Trade-off Table

| Approach | Explanation quality | Speed | Memory | Hallucination risk | Implementation complexity |
|---|---|---|---|---|---|
| SHAP only | Low (numbers, not prose) | Very fast | Negligible | None | Very low |
| LIME only | Low | Moderate | Negligible | None | Very low |
| Template + SHAP | Moderate (rigid prose) | Very fast | Negligible | None | Low |
| Decoder-only, no structure | Low–Moderate | Moderate–Slow | High | High | Moderate |
| Decoder + all features, no SHAP | Moderate | Moderate–Slow | High | Moderate | Moderate |
| **SHAP + SIR + Decoder (proposed)** | **High** | **Moderate–Slow** | **High** | **Low** | **High** |
| Full LLM (GPT-4-class) | Very high | Very slow | N/A (cloud) | Low–Moderate | Low |

## 6. For Resource-Constrained Environments: Most Effective and Practical Approach

The question for a resource-constrained environment is: which trade-offs can you accept? Here is a tiered recommendation based on available hardware.

### Tier 1: Highly Constrained (≤4GB RAM, ARM Cortex-A53, CPU only)
Target: Raspberry Pi 4 / NXP i.MX 8M Plus

**Recommended approach:**
- XGBoost classifier (always-on, <5MB, ~2µs)
- Encoder SLM: TinyBERT INT8 ONNX (~14MB, ~157ms)
- SHAP: Tree SHAP on XGBoost (<100ms)
- SIR: constructed as described, minimal size (top 4 features only)
- Decoder: Phi-2 Q4_K_M (~1.7GB, 2–5 tokens/second → ~60–100s per explanation)
- Async queue: mandatory — explanation latency is 1–2 minutes

**The key trade-off here:** At this hardware tier, explanation generation takes 1–2 minutes, not 1–3 seconds. This is still acceptable architecturally because explanations are advisory (the detection and blocking happen in milliseconds). But it must be disclosed as a limitation in your thesis, and it must be measured on actual hardware using CodeCarbon.

**Practical advice:** For Tier 1, consider whether real-time explanation generation is even the right goal. An alternative design: accumulate SIRs in a queue, batch-process explanations every 5 minutes, and deliver a "security digest" to the analyst rather than per-alert explanations. This matches the hardware reality better.

### Tier 2: Moderately Constrained (4–8GB RAM, ARM Cortex-A55 or Jetson Nano)
Target: Raspberry Pi 5 / NVIDIA Jetson Nano (128-core Maxwell GPU)

**Recommended approach:** Full proposed architecture as described.
- TinyBERT or MiniLM INT8 ONNX
- SHAP + full SIR (top 5–6 features)
- Gemma3-4B Q4_K_M via Ollama (~2.5GB, 3–8 tokens/second with speculative decoding)
- Explanation latency: 30–120 seconds

### Tier 3: Edge Server (8–16GB RAM, Intel NUC or similar x86 SBC)

**Recommended approach:** Full proposed architecture, decoder can be Gemma3-4B or even 7B Q4_K_M.
- MiniLM or SecurityBERT ONNX
- Explanation latency: 5–30 seconds

### Most Practical Recommendation for Your Research

Given that this is a research project (not production deployment), and given that you need to demonstrate feasibility rather than achieve minimum latency:

**Run training and evaluation on a development machine (GPU workstation or cloud GPU). Measure inference performance on the target embedded hardware.** The 14× slowdown rule gives you the embedded estimate from desktop measurements. You do not need to run all experiments on the actual IoT device — you need to measure inference latency and RAM usage on it to validate feasibility.

**For the thesis contribution:** The detection pipeline (XGBoost + Encoder SLM) must be demonstrated on actual resource-constrained hardware with measured latency and RAM. The decoder pipeline can be evaluated primarily on the development machine, with embedded performance estimated using the 14× rule and validated with a sample run on the target device.

## 7. What Requires Training? Complete Component-by-Component Analysis

This is a crucial question for planning your research timeline. Here is an exact breakdown of every component.

### Components That MUST Be Trained or Fine-Tuned

---

**Component 1: XGBoost Classifier**

- **Requires training:** Yes, from scratch
- **On what data:** CIC IIoT 2025 labeled tabular feature vectors (12–15 features)
- **How long:** 5–20 minutes on a standard laptop CPU
- **What you do:** `xgb_model.fit(X_train, y_train)` with cross-validated hyperparameter tuning
- **Output:** Serialized model file (~3MB), saved with `joblib.dump()`
- **No pre-trained alternative exists for network traffic**

---

**Component 2: Feature Scalers (MinMaxScaler, StandardScaler)**

- **Requires fitting:** Yes (not "training" in the deep learning sense, but must be fitted on training data)
- **On what data:** Training split of CIC IIoT 2025 features
- **How long:** Seconds
- **What you do:** `scaler.fit(X_train)` then save with `joblib.dump(scaler, 'scaler.pkl')`
- **Critical:** Must be fitted on training data only. Fitted parameters saved and applied to all future data (validation, test, deployment)

---

**Component 3: Encoder SLM (TinyBERT / MiniLM / SecurityBERT)**

- **Requires fine-tuning:** Yes — start from pre-trained checkpoint, fine-tune on your data
- **Starting point:** Download pre-trained checkpoint from HuggingFace Hub:
  - `huawei-noah/TinyBERT_General_4L_312D`
  - `microsoft/MiniLM-L6-H384-uncased`
- **On what data:** CIC IIoT 2025 verbalized flow features (Format B text strings) with attack class labels
- **How long:** 2–6 hours on a single GPU (RTX 3090/4090 or equivalent cloud GPU)
- **What you do:** Replace classification head, fine-tune all layers with AdamW lr=2e-5, 5 epochs, early stopping
- **Output:** Saved HuggingFace checkpoint → exported to ONNX → quantized to INT8
- **The ONNX export and INT8 quantization require no training** — they are post-training transformations

---

**Component 4: Decoder SLM (Gemma3-4B-Instruct / Phi-2 / LLaMA3.2-3B-Instruct)**

- **Requires fine-tuning:** Yes — QLoRA fine-tuning on instruction dataset
- **Starting point:** Download instruct-tuned base model from HuggingFace Hub (Gemma3-4B-Instruct, etc.)
- **On what data:** Teacher-generated (SIR JSON → explanation) instruction pairs
  - You first generate 500–5,000 training examples by calling GPT-4 or Claude with SIR JSONs from your dataset
  - Human-review 10% for quality control
  - This dataset creation is offline, one-time work
- **How long:** 2–4 hours on a single 24GB GPU (RTX 3090/4090 or A10G cloud instance)
- **What you do:** QLoRA with bitsandbytes + PEFT, LoRA rank=8, alpha=32, 3–5 epochs, SFTTrainer
- **Output:** LoRA adapter checkpoint → merge → convert to GGUF → quantize to Q4_K_M
- **The merge, GGUF export, and quantization require no further training**

---

**Component 5: XGBoost Retriever (for exemplar selection)**

- **Requires training:** Yes, but this is a simpler option with an even simpler alternative
- **Option A — Train an XGBoost retriever:** Train a small classifier to map from feature vectors to exemplar index. Requires labeled (feature_vector → exemplar_id) pairs.
- **Option B (recommended for simplicity):** Use Euclidean distance or cosine similarity on the normalized tabular vector to find the closest exemplar. No training required. For a library of 15–25 exemplars, a linear scan (compute distance to each exemplar) takes microseconds.

For your thesis, **Option B is sufficient and removes one training step.** The XGBoost retriever is only marginally better than simple Euclidean distance for a small library.

## 8. Final Recommendation: Best Design Choice for Your Research

### What to Keep (Do Not Change)

**Keep the three-component detection pipeline (XGBoost + Encoder SLM + SHAP).** The evidence strongly supports this design:
- XGBoost as the gate is computationally essential for constrained hardware
- Encoder SLM adds accuracy and produces the `[CLS]` embedding
- SHAP is fast, exact, and measurably improves explanation quality
- This combination is validated across seven papers in your literature review

**Keep the SIR.** It is the critical anti-hallucination mechanism. The eX-NIDS paper's finding (correctness 36% → 80% with augmented prompt) is direct evidence that structured, attribution-grounded prompts are worth the engineering effort. The SIR adds essentially zero computational cost (it is Python dictionary construction).

**Keep the async queue.** The decoder's latency makes synchronous integration architecturally impossible at any hardware tier. The queue is not a design complexity — it is a necessity.

**Keep the SSRP framework.** The 40% improvement in explanation quality for 2–4B models is validated by Paper F3-9. The 16 factors are not burdensome — most of them are static text loaded once at startup. The effort to write them is a few hours; the quality improvement is permanent.

### What to Simplify (Reduce Complexity Without Losing Quality)

**Simplify the exemplar retriever.** Replace the XGBoost retriever with simple Euclidean distance on the normalized feature vector. For a library of 15–25 exemplars, this is microsecond-fast and requires no training. The quality difference between a trained XGBoost retriever and simple distance on a small library is marginal.

**Consider Option B for SIR features (no SHAP) if system complexity is a concern.** You can include all 12–15 features with precomputed direction labels (above/below benign mean) without computing per-sample SHAP values. This removes the runtime SHAP dependency while preserving the SIR structure and most of its anti-hallucination benefit. However: since Tree SHAP adds only <100ms and the encoder SLM already takes 80ms, keeping SHAP does not significantly increase latency. Only simplify here if you have a specific reason.

### What Your Research Contribution Actually Is

Your thesis contributes all of these (all are validated as research gaps):

1. **First application of compact encoder SLM (TinyBERT/MiniLM/SecurityBERT class) specifically to Slowloris, RUDY, and Slowread attack flows** — no prior paper does this
2. **First dual SLM pipeline (encoder for detection + decoder for explanation) demonstrated on resource-constrained IoT edge hardware** — prior hybrid systems use cloud-hosted GPT-4 or GPT-3.5 for the explanation component
3. **First specification and evaluation of SHAP→SIR→Decoder bridge for slow-rate DoS explanation** — the interface is novel even if each component individually exists
4. **First evaluation on CIC IIoT Dataset 2025** — new dataset, no prior published results
5. **Empirical measurement of the latency, RAM, and energy cost of dual SLM on actual ARM hardware** — the 14× slowdown rule provides a rough estimate but your measurement on the actual device is original empirical data

The architecture is not just an engineering project — each design choice maps to a research contribution and is justified by prior literature that shows the problem it is solving.

### One Final Caution

The decoder SLM inference time on Raspberry Pi-class hardware (30–150 seconds per explanation) is the biggest practical challenge in your design. Be honest about this in your thesis. Frame the contribution as: "We demonstrate that a dual SLM pipeline for detection and explanation is architecturally feasible on resource-constrained IoT hardware, with detection latency of <200ms (suitable for real-time blocking) and explanation latency of X seconds (suitable for asynchronous analyst review)." Do not overclaim that explanation is "real-time" — it is not on constrained hardware, and the literature does not claim it is either.
